# 🛠 Техническое задание для Backend-разработчика

Привет! Твоя зона ответственности — **бизнес-логика, проектирование структуры PostgreSQL, оптимизация запросов и разработка API** для системы аудита инфраструктуры «АЛРОСА ИТ».

Инфраструктура уже развернута (Docker Compose, Nginx, PostgreSQL, CI/CD в GitHub Actions). Твоя задача — расширять бэкенд, соблюдая архитектурные стандарты проекта.

---

## ⚠️ Правила работы (Architectural Constraints)

1. **Не ломай существующий контракт:**  
   Фронтенд уже работает с эндпоинтами из `API_CONTRACT.md`. Если ты меняешь формат ответа, сначала согласуй это с командой.
2. **Безопасность потоков и синхронность:**  
   Если функция выполняет операции с базой через SQLAlchemy (`db.query`) или Pandas (`pd.read_csv`), объявляй эндпоинт как обычный `def`, а не `async def` (чтобы FastAPI отдавал задачу в threadpool и не блокировал Event Loop).
3. **Pydantic-схемы обязательны:**  
   Все входящие (`Request`) и исходящие (`Response`) данные должны валидироваться через схемы Pydantic в `backend/app/schemas/`.
4. **Тесты перед коммитом:**  
   В проекте настроен CI/CD. Перед отправкой ветки обязательно выполни локально:
   ```bash
   docker compose exec backend pytest tests/
   ```
   Если тесты падают, GitHub Actions заблокирует билд.

## 🎯 Бэклог задач (Что нужно реализовать)

### 1. Декомпозиция `main.py` на `APIRouter` (Архитектурный рефакторинг)
**Проблема:** Сейчас все эндпоинты свалены в `main.py`.  
**Задача:** Разнести логику по роутерам в папку `backend/app/api/v1/`:
* `api/v1/audit.py` — загрузка реестров, получение результатов, история.
* `api/v1/catalog.py` — справочники ОС, реестр софта, правила совместимости.
* `api/v1/stats.py` — агрегации, распределение по волнам, блокирующий софт.
В `main.py` должно остаться только подключение роутеров: `app.include_router(...)`.

---

### 2. Пагинация и фильтрация рабочих мест
**Проблема:** Если в загруженном файле 5 000 компьютеров, передавать весь массив в JSON целиком нельзя — фронтенд зависнет.  
**Задача:** Реализовать эндпоинт:
`GET /api/v1/audit/{session_id}/workstations`
**Query-параметры:**
* `page` (int, default=1) — номер страницы.
* `page_size` (int, default=50) — количество записей.
* `status` (string, optional) — фильтр: `ready`, `upgrade_required`, `blocked`.
* `department` (string, optional) — фильтр по подразделению.
* `search` (string, optional) — поиск по имени хоста или ФИО пользователя.
**Формат ответа:**
```json
{
  "total": 1250,
  "page": 1,
  "page_size": 50,
  "total_pages": 25,
  "items": [ ... ]
}
```

---

### 3. CRUD-интерфейс справочника ПО и правил совместимости
**Проблема:** Справочник ПО сейчас статический (заполняется только при сидировании). Пользователь должен иметь возможность через интерфейс добавлять новый софт и менять отечественные аналоги.  
**Задача:** Реализовать эндпоинты:
* `POST /api/v1/catalog/software` — добавление новой программы (название, категория).
* `POST /api/v1/catalog/compatibility` — создание нового правила совместимости.
* `PUT /api/v1/catalog/compatibility/{id}` — редактирование правила (изменение флага `is_blocker`, статуса, рекомендованного отечественного аналога).
* `DELETE /api/v1/catalog/compatibility/{id}` — удаление правила.

---

### 4. Экспорт аналитического среза в CSV
**Задача:** Реализовать эндпоинт выгрузки отфильтрованных данных аудита:
* `GET /api/v1/audit/{session_id}/export/csv` — отдает CSV-файл с готовым планом миграции по выбранной сессии (заголовки `Content-Disposition: attachment; filename=...`).

### 5. Покрытие предметной логики автотестами
**Задача:** Добавить в `backend/tests/`:
* `test_scoring.py` — проверка функции вычисления готовности железа (RAM, CPU, диск).
* `test_rules.py` — проверка логики блокирующего ПО и назначения волн миграции (Волна 1, 2, 3).
