# Доработка групповых политик и проверка проекта

Проверено 22 ноября 2026 года на локальном Docker Desktop с настоящей PostgreSQL 16. Основная задача — независимые критерии и правила ПО для групп рабочих мест.

## Что исправлено

| Найденная проблема | Изменение |
| --- | --- |
| Общие веса и общий JSON-файл блокираторов | Независимые политики department в PostgreSQL с миграцией исходных настроек |
| Клиент и сервер по-разному назначали волны | Согласованные условия волн, приоритет локальных правил и проверки пограничных случаев |
| Пользовательские блокираторы не участвовали в серверном аудите | Применение правил группы при загрузке каждой строки и сохранение результата |
| Ответ upload терял список станций из-за response_model | Список workstations включён в контракт ответа |
| История не возвращала установленные программы | Исходный список хранится в JSON, включая неизвестные каталогу названия |
| Каталог объединял пользовательские правила с искусственными id без группы | Клиентский каталог учитывает выбранную ОС и только политику выбранной группы |
| Нативные статусы отображались как аналоги | Согласование интерфейса с native_ready |
| При повторном открытии терялась целевая ОС | В ответ истории добавлено имя ОС, клиент восстанавливает выбор |
| В статистику не попадали неизвестные каталогу блокираторы | Для них используется сохранённое название из диагностического сообщения |
| Карточки оборудования использовали общие пороги | Карточка получает пороги собственной группы |
| Backend не применял Alembic до старта | Миграция включена в запуск контейнера, добавлены readiness и зависимость Nginx |
| Сборка frontend использовала npm install | npm ci и зафиксированный package-lock.json |
| API-тесты обращались к защищённым маршрутам без JWT | Реальная авторизация тестового клиента и отдельные проверки запретов |
| Некорректная инвентаризация доходила до ошибок записи | Валидация целых значений, идентификаторов, дублей, групп и лимитов файла |
| Резервный ML-расчёт показывал метрики модели | Явный inference_mode, отсутствие фиктивных метрик у эвристики |
| Недоступная LLM могла помечать неизвестное название как непрограммную сущность | Честный статус ручной проверки без выдуманной уверенности |
| В интерфейсе было сообщение об отключении ПК от внешней системы | Удалено неподтверждённое описание, интерфейс сообщает о локальном правиле |
| CSV-отчёт не экранировал поля | Экранирование разделителей, кавычек и префиксов формул в основном отчёте |

## Проверенный результат

- Backend: 24 теста прошли, покрытие 82%, скоринг 97%.
- Клиентский движок: 9 тестов прошли.
- Ruff: E9, F63, F7, F82 без ошибок. Полный стилевой линтинг и статическая типизация не заявляются.
- Production-сборка frontend и оба Docker-образа собраны.
- Все три сервиса запускаются. Backend и БД имеют healthcheck, /ready через Nginx вернул database=reachable.
- Миграция на пустой тестовой БД, downgrade новой ревизии и повторный upgrade выполнены успешно.
- scripts/demo.py создал 6 синтетических станций: 2 ready, 2 upgrade_required, 2 blocked.
- В браузере проверены вход, обзор, выбор инженерной группы с 16 ГБ ОЗУ, групповой каталог, реестр блокираторов, ML и карточки станций.
- CI расширен проверкой миграций, клиентских тестов и полного запуска Compose. Итог удалённого прогона следует смотреть в GitHub Actions.

Использована отдельная тестовая база alrosa_audit_test. Учебный демонстрационный набор находится в alrosa_audit, его группы имеют префикс «Демо:».

## Границы результата

Групповые политики не реализуют автоматически разграничение доступа к данным разных подразделений. Роли регулируют право чтения и редактирования. Доступ к аудитам требует отдельной проверки перед внешним внедрением.

ML-оценка не отменяет детерминированный блокер. Обучение использует синтетические данные, производственное качество и экономический эффект не подтверждены. Включённая модель загрузилась и выполнила инференс на демостенде, резервная эвристика отдельно покрыта тестом.

История сохраняет оценки на момент загрузки, но не полную версию политики. Новые правила применяются в предпросмотре и новых аудитах. Для воспроизведения всего контекста старой оценки нужен следующий этап: версионность правил.

Неизвестные названия ПО, утраченные старыми версиями приложения, нельзя восстановить миграцией. Для старых записей восстанавливаются только известные связи каталога.

Python-зависимости остаются с нижними границами версий исходного проекта. Локальная проверка успешна с установленными на момент сборки пакетами. Отдельный lock-файл Python и регулярное обновление зависимостей могут стать следующей задачей.
