# Демонстрация командного проекта

Цель выступления — показать совместно работающий сервис и проверить результат каждого участника на одном сценарии. Рекомендуемая длительность основной части — 7–9 минут, затем вопросы.

## Подготовка

Запустить Docker Desktop и выполнить команды README. Запустить scripts/demo.py. Открыть интерфейс и пройти вступительный экран. Перед защитой проверить /ready и открыть последний успешный запуск GitHub Actions. Учётная запись демостенда указана в README.

## Выступление команды

Виктория открывает задачу кейса, объясняет входные данные и архитектуру API. Показывает Swagger, ролевую модель и то, что сервер сохраняет результаты проверки. Важно объяснить различие между автоматической оценкой и подтверждением совместимости в пилоте.

Артур показывает обзор, карточки рабочих мест, фильтр по отделу, волны и экспорт отчёта. На демонстрационном наборе видны шесть рабочих мест: два готовых, два требующих действий и два заблокированных. Это учебный набор, не статистика предприятия.

Алексей демонстрирует инфраструктуру и БД. Команда docker compose ps показывает состояния сервисов, /ready подтверждает соединение API с PostgreSQL, alembic current показывает ревизию схемы. В GitHub Actions видны проверки backend, frontend и полного контейнерного запуска. Это проверяемые результаты DevOps, даже если у них нет отдельного продуктового экрана.

Затем Алексей открывает «Критерии», выбирает «Демо: инженеры» и показывает минимум 16 ГБ ОЗУ. Для «Демо: офис» минимум 4 ГБ. В «Политики и NLP» показывает DemoCAD как blocker у инженеров и native_ready у офиса. WS-001 и WS-002 имеют одинаковое оборудование и ПО, но сервер назначает волны 1 и 3. Правило применяется только внутри своей группы.

В ML-разделе Алексей показывает режим расчёта, факторы риска и сценарий модернизации. Следует назвать источник данных синтетическим. Резервная эвристика обозначается отдельно. Сценарное изменение риска не доказывает реальное снижение числа инцидентов.

В завершение Виктория или вся команда формулирует результат: инвентаризация превращается в объяснимый план перехода с учётом подразделений. Следующие этапы — версии политик, проверка на реальном парке и развитие контроля доступа.

## Команды для наглядного DevOps-результата

~~~sh
docker compose ps
docker compose exec backend alembic current
docker compose exec db psql -U audit_user -d alrosa_audit -c "SELECT group_name FROM group_policies ORDER BY group_name;"
docker compose exec db psql -U audit_user -d alrosa_audit -c "SELECT workstation_ext_id, department, installed_software FROM workstations ORDER BY id DESC LIMIT 6;"
~~~

После перезапуска backend открыть историю: список ПО и серверные оценки остаются в PostgreSQL. Временная остановка backend для демонстрации возможна, но её нужно закончить до перехода к показу интерфейса.

## Ответы на вероятные вопросы

**Почему нужна политика группы?** Одни и те же программы и характеристики могут иметь разную значимость для разных подразделений. Например, локальное исключение согласовано для одной группы и отсутствует в другой.

**Можно ли считать метрики ML доказанным качеством?** Только на использованной синтетической выборке, если метрики получены соответствующим обучением. Качество на реальных рабочих местах пока не подтверждено.

**Что делает CI/CD?** Проверяет код, тесты, миграции, сборку и запуск контейнеров. Автоматического развёртывания на сервере предприятия в репозитории нет.

**Как доказывается результат DevOps?** Повторяемым запуском на чистой БД, состояниями healthcheck, версией Alembic, успешным CI и сохранением аудита после перезапуска.

**Что готово, а что требует развития?** Групповые политики, аудит, история и интерфейс реализованы. Версионность правил, продуктивная эксплуатация, аудит доступа к чужим подразделениям и валидация на реальных данных остаются отдельными задачами.
