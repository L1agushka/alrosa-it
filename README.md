# ALROSA IT

Учебный командный проект АВТ-551: аудит готовности рабочих мест к переходу на отечественное ПО. Сервис принимает инвентаризацию CSV/XLSX, проверяет оборудование и ПО, формирует волны миграции и сохраняет историю в PostgreSQL.

## Запуск

Требуются Docker Desktop с Linux-контейнерами и Docker Compose.

~~~sh
git clone https://github.com/L1agushka/alrosa-it.git
cd alrosa-it
docker compose up -d --build
~~~

- Интерфейс: [localhost](http://localhost)
- Документация API: [Swagger](http://localhost/docs)
- Живость процесса: [health](http://localhost/health)
- Готовность с подключением к БД: [ready](http://localhost/ready)

Демонстрационная учётная запись: `admin@alrosa.ru`, пароль `admin123`. Это локальный учебный стенд. Перед внешним развёртыванием нужны собственные учётные данные, SECRET_KEY, HTTPS и проверка разграничения данных.

Backend применяет `alembic upgrade head`, затем запускает API и идемпотентное сидирование справочников. Nginx стартует после успешной проверки готовности backend. PostgreSQL хранит данные в томе `pgdata` и не публикует порт на хосте. Из образа исключены локальные кэши, production-процесс не использует autoreload и bind mount исходников.

## Политики групп

Группа — значение колонки `department` во входном файле. Например, бухгалтерия и инженерный отдел получают независимые требования к ОЗУ, CPU, диску, доле неизвестного ПО, весам и пользовательским правилам.

1. Откройте «Критерии» и выберите или создайте группу.
2. Задайте пороги и веса, сохраните политику группы.
3. В «Политики и NLP» выберите ту же группу, добавьте блокираторы, разрешённые исключения или условия ручной проверки.
4. Загрузите инвентаризацию. Сервер выберет политику отдельно для каждой строки.

Локальное правило имеет приоритет над базовым каталогом совместимости. Если подходят несколько правил, выигрывает наиболее длинный паттерн. Минимумы ОС нельзя снизить политикой группы. Изменения в браузере показывают текущий предпросмотр. Исторический результат остаётся прежним, новый снимок создаётся повторной загрузкой.

Подробности и контракты API: [docs/POLICIES.md](docs/POLICIES.md).

## Волны миграции

| Волна | Условие |
| --- | --- |
| 1 — ready | По применённым правилам проблем не обнаружено |
| 2 — upgrade_required | Требуется модернизация, проверка неизвестного ПО или действие по локальному правилу |
| 3 — blocked | Есть блокер ПО или аппаратный критерий с весом от 50 |

Вес задаёт приоритет проблемы. Нулевой вес не отменяет блокер или необходимость проверки. Совместимость конкретных версий ПО и оборудования подтверждается пилотом, справочник прототипа не является сертификацией поставщика.

## Воспроизводимая демонстрация

~~~sh
docker compose cp scripts backend:/app/scripts
docker compose exec backend python scripts/demo.py --base-url http://localhost:8000
~~~

Скрипт создаёт три группы с префиксом «Демо:» и загружает шесть синтетических рабочих мест. Он настраивает эти демонстрационные группы повторно при каждом запуске. Ожидаемый результат: две станции в каждой волне. DemoCAD разрешён для офисной группы и блокирует инженерную. Это вымышленная программа, специально введённая для наглядной проверки.

Сценарий защиты и распределение выступления: [docs/DEFENSE.md](docs/DEFENSE.md).

## Проверки

CI выполняет линтер backend, миграцию вперёд/назад/вперёд на временной PostgreSQL, pytest с покрытием, клиентские тесты скоринга, production-сборку и запуск Docker Compose с проверкой readiness и демонстрационного сценария.

~~~sh
docker compose exec backend ruff check app --select E9,F63,F7,F82
~~~

Для интеграционных тестов используйте отдельную БД и передавайте её через DATABASE_URL. Тесты создают и удаляют учебные записи. Пример для локального контейнера PostgreSQL:

~~~sh
docker compose exec db psql -U audit_user -d alrosa_audit -c "CREATE DATABASE alrosa_audit_test;"
docker compose exec -e DATABASE_URL=postgresql+psycopg://audit_user:audit_password@db:5432/alrosa_audit_test backend alembic upgrade head
docker compose exec -e DATABASE_URL=postgresql+psycopg://audit_user:audit_password@db:5432/alrosa_audit_test backend pytest --cov=app tests/
~~~

Клиентские проверки из каталога frontend: `npm ci`, `npm test`, `npm run build`.

## ML и NLP

ML-раздел использует включённую в репозиторий Random Forest, если загрузка и инференс успешны. При сбое включается явно обозначенная эвристика. Метрики модели и важность признаков не показываются как результат эвристики. Данные обучения синтетические, метрики из meta.json не подтверждают качество на реальном парке.

Сценарии модернизации выполняют повторный серверный инференс той же моделью на изменённых признаках. Ручные скидки риска и вымышленные расчёты часов/бюджета удалены. Сценарий не меняет сохранённый аудит и не доказывает причинный эффект модернизации. Подробности обучения, проверки и ограничений: [docs/ML.md](docs/ML.md).

NLP сначала проверяет правила группы и словарь RapidFuzz. Для обнаружения неизвестного ПО нужна отдельно развёрнутая Ollama с Qwen. В базовом Compose её нет. Недоступность LLM переводит неизвестный запрос на ручную проверку.

## Ограничения прототипа

- Ролевая модель admin/analyst/viewer есть, но границы доступа к аудитам отдельных подразделений требуют самостоятельной проверки перед внедрением.
- Первоначальные справочники содержат учебные соответствия ПО, которые нужно актуализировать под версии и лицензии.
- Исторические снимки сохраняют результаты, но не версию всего набора правил. Полный журнал изменений политик — следующий этап.
- Старые аудиты до новой миграции восстанавливают список только известного каталогу ПО из связующей таблицы. Ранее утраченные неизвестные названия восстановить нельзя.
- Миграция копирует прежние глобальные политики в независимые политики существующих групп. Новые группы получают собственную копию базовых значений. Общий JSON-файл перестаёт быть активным хранилищем правил.

Изменения и проверяемые результаты: [docs/REVIEW.md](docs/REVIEW.md).


Для презентационных снимков: `docker compose exec backend python scripts/demo.py --base-url http://localhost:8000 --large` (после копирования scripts в контейнер). Это отдельный синтетический набор на 120 рабочих мест; обычный запуск сохраняет проверку на шести станциях.
