## 👥 Многопользовательский режим и разграничение доступа (RBAC & Multi-Tenant)

### Цель задачи

Обеспечить безопасную работу распределённых подразделений компании (ГОКи, экспедиции, дирекции) в единой платформе: защитить API авторизацией, изолировать данные аудитов между филиалами и разграничить доступ по ролям.

---

### 1. Ролевая модель доступа

| Роль | Область видимости данных | Доступные действия |
| --- | --- | --- |
| **`superadmin`** *(Корпоративное ИТ)* | Все подразделения и ГОКи | Полный доступ: управление пользователями, редактирование справочников ОС/ПО, просмотр и удаление любых сессий. |
| **`department_admin`** *(Начальник ИТ ГОКа)* | Только своё подразделение | Просмотр всех аудитов своего ГОКа, создание учётных записей инженеров филиала, экспорт сводных отчётов. |
| **`auditor`** *(Системный администратор)* | Только своё подразделение | Загрузка CSV/Excel, запуск скоринга, просмотр собственных аудитов и сессий коллег по подразделению. |
| **`viewer`** *(Руководство / Аудит)* | Назначенное подразделение | Режим чтения (*Read-Only*): дашборд, карта готовности, фильтры, скачивание отчётов. Загрузка данных заблокирована. |

---

### 2. Требования к реализации

#### Архитектура данных (SQLAlchemy)

1. **Модель `Department`:** справочник подразделений (`id`, `name`, `code`, `created_at`).
2. **Модель `User`:** сотрудники (`id`, `email`, `hashed_password`, `full_name`, `role`, `department_id`, `is_active`).
3. **Обновление `AuditSession`:**
* Добавить внешние ключи `owner_id` (ссылка на `users.id`) и `department_id` (ссылка на `departments.id`).
* Добавить флаг `is_shared_with_dept` (доступен ли аудит другим инженерам подразделения).



#### Аутентификация и безопасность

* Реализовать схему **OAuth2 Password Bearer** с выпуском подписанных JWT-токенов (`HS256`).
* Хеширование паролей через `passlib` (`bcrypt`).
* Срок жизни: `access_token` — 60 минут, `refresh_token` — 7 дней.
* Написать dependency-фильтр FastAPI (`get_current_user`, `RoleChecker`) для автоматической валидации токена и проверки ролей перед вызовом эндпоинтов.

#### Изоляция данных (Data Scoping)

* При запросе списков аудитов (`GET /api/v1/audit/sessions`) выполнять автоматическую фильтрацию по `department_id` текущего пользователя.
* Прямой доступ по идентификатору (`GET /api/v1/audit/{id}`) к сессии чужого филиала должен возвращать статус `404 Not Found` (или `403 Forbidden`).

---

### 3. Спецификация API

* **`POST /api/v1/auth/token`** — авторизация по паре логин/пароль (`application/x-www-form-urlencoded`), выдача JWT-токенов.
* **`POST /api/v1/auth/refresh`** — выпуск нового `access_token` по валидному refresh-токену.
* **`GET /api/v1/auth/me`** — получение информации о текущем авторизованном пользователе.
* **`GET /api/v1/admin/users`** — список пользователей филиала/системы (доступно только админам).
* **`POST /api/v1/admin/users`** — регистрация нового сотрудника с привязкой к роли и подразделению.
* **`POST /api/v1/audit/upload`** — автоматическая привязка создаваемой сессии к `user.id` и `user.department_id`.
