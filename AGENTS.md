# ALROSA IT: правила работы Codex

## Область и разрешения

Проект — инженерная система оценки миграции Windows → Astra Linux и другие отечественные ОС. Улучшения UI должны помогать принимать проверяемые решения о парке, а не создавать впечатление гарантированной совместимости.

Подготовка инструкций и скилла не разрешает редизайн. Начинать его только после отдельного разрешения пользователя. При будущих задачах редизайна применять `.agents/skills/migration-ui-design/SKILL.md`.

Существующий `.clinerules` содержит правила маркетинговых страниц. Для аналитических экранов его требования к обязательным анимациям, стеклянной навигации, конверсионным секциям, фиксированным шрифтам и значениям не применять вопреки настоящим правилам и явным указаниям пользователя. Сам файл не переписывать без задачи. Существующие незакоммиченные изменения пользователя сохранять.

## Защита функциональности

- Не изменять алгоритмы совместимости, пороги, приоритеты блокеров и распределение по волнам без отдельного разрешения; это относится и к frontend, и к backend, ML и локальным эвристикам.
- Не менять API, форматы импорта/экспорта, схемы данных, props и callbacks компонентов ради визуального улучшения.
- Не изменять авторизацию, хранение пользователя, БД, миграции, seed, backend и инфраструктуру ради дизайна.
- Не удалять функции, действия, фильтры, состояния, сведения и способы доступа к ним. Перекомпоновка должна сохранять доступность возможностей.
- Не заменять реальные результаты вымышленными. Не добавлять фиктивные характеристики, ПО, периферию, аналоги, стоимости, проценты, причины и рекомендации.
- Не добавлять зависимости без обоснования и согласования. Использовать текущие React, CSS и SVG.
- Выявленное несоответствие данных или алгоритмов описать отдельно; не исправлять скрытно в рамках редизайна.

## Карта проекта (проверена по исходникам)

- Frontend: React 19, Vite 8, JavaScript/JSX, обычный CSS; версии сверять с `frontend/package.json`, README местами устарел. `src/main.jsx` → `App.jsx`; навигация через локальный `page`, без router. Состояние через React hooks, запросы через fetch. Vite проксирует `/api` на порт 8000; production обслуживается nginx.
- Backend: FastAPI, Pydantic 2, SQLAlchemy 2, PostgreSQL 16, Alembic; pandas/openpyxl для импорта, scikit-learn/joblib для ML, RapidFuzz/NLP и Ollama для политик. Слои: `backend/app/api/v1`, `schemas`, `models`, `services`, `core`; контейнеры в `docker-compose.yml`. `ml/` содержит обучение и генераторы данных, не UI.
- Экраны App: обзор, рабочие места, критерии/каталог ПО, волны перехода, отчёт, конфигуратор, ML-аналитика, политики/NLP. `Welcome.jsx` — входной экран; выбор оператора в localStorage не считать доказательством серверной авторизации.
- Компоненты: `Workstations.jsx` — карточный реестр с поиском по ID/пользователю/отделу, фильтрами, сортировкой и дозагрузкой; `WorkstationModal.jsx` — детали, ПО, локальная оценка риска, what-if, копирование playbook; `Mosaic.jsx`/`Office.jsx` — визуализация парка; `Builder.jsx` — отдельный конфигуратор со статическими вариантами; `SoftwareCatalog.jsx`, `MLAnalytics.jsx`, `RulesAndNLPTab.jsx`; общие элементы в `ui.jsx`.
- Дизайн-система не выделена в библиотеку: CSS-переменные `.app` в `App.css`, базовые стили в `index.css`, отдельный `landing.css`, встроенные стили JSX. Идентичность: ALROSA IT, огранённый алмаз, тёмная технологичная палитра, ледяной голубой акцент, Manrope в приложении, зелёный/янтарный/красный для статусов. Перед изменениями учитывать каскад всех трёх CSS и inline styles.

## Поток данных и оценка

1. `App.jsx` загружает `/api/v1/catalog/os`, `/catalog/compatibility`, `/catalog/software`, `/audit/history`, `/audit/latest` и статистику. Импорт отправляет FormData `file` + `target_os` в `POST /api/v1/audit/upload`.
2. `services/parser.py`: CSV UTF-8 BOM с автоопределением разделителя; также `.xls/.xlsx` через pandas. Обязательные поля: `workstation_id`, `department`, `ram_gb`, `cpu_cores`, `disk_gb`. Дополнительные используемые поля: `user_fullname`, `current_os`, `installed_software` (имена через `;`). Текущий frontend file picker ограничен CSV; не расширять контракт импорта в рамках оформления.
3. `services/scoring.py`: RAM/ядра/общий объём диска сравниваются с профилем ОС; правила ПО сопоставляются по имени без учёта регистра. Блокер ПО имеет приоритет: `blocked`/3; иначе дефицит железа: `upgrade_required`/2; иначе `ready`/1. Отсутствие правила ПО не создаёт блокер, но это не подтверждение совместимости.
4. Сессия, устройства, оценки и блокеры сохраняются в БД; связь установленного ПО записывается для найденных в каталоге имён. Проверять модели и Pydantic-схемы отдельно от возвращаемого словаря сервиса.
5. На frontend `mapServerWorkstations` адаптирует ответ, затем `engine.js:evaluate` заново считает RAM/ядра и долю ПО без аналога; диск в этом пересчёте не проверяется. UI-статусы: «Готов»/1, «Частично»/2, «Не готов»/3. Эти результаты могут расходиться с сервером. Нельзя незаметно унифицировать алгоритмы.
6. В реестре CPU представлен количеством ядер, RAM — ГБ и сегментами относительно порога, ПО — счётчиками. Диск отображается в деталях как общий объём ГБ. Модель CPU, архитектура, типы/модели накопителей и реальная инвентаризация периферии не представлены текущим контрактом устройства; не выдумывать их. `peripherals_count = 2` в ML — константа, не измерение.

## Известные ограничения, которые нельзя маскировать дизайном

- `AuditUploadResponse` не содержит `workstations`, хотя frontend ожидает их после upload. `WorkstationRead` не выдаёт установленное ПО; адаптер не сохраняет его полный список. История доступна в API, но состояние истории в App не означает существование UI переключателя.
- Адаптер подставляет RAM 8, CPU 4, диск 256 и количество программ 4 при отсутствии/нуле; карточка устройства имеет запасной список ПО. Это не подтверждённые данные инвентаризации.
- «SHAP» в `WorkstationModal.jsx` вычисляется локальными фиксированными правилами; не представлять его как полученную SHAP-декомпозицию обученной модели. ML endpoint имеет собственные модельные/резервные оценки; отличать их от детерминированного аудита. Стоимость и эффект what-if — оценки, а не подтверждённые закупочные данные.
- Каталог и рекомендации имеют статические запасные значения. Наличие аналога не гарантирует совместимости исходного ПО, функциональной эквивалентности, драйверов, лицензирования или сертификации Astra Linux.
- Кнопка анализа в App переключает экран и запускает визуальную фазу; не считать её новым серверным аудитом.

При редизайне явно отделять исходные данные, результат правил, предположение и неизвестность. Если честное отображение требует изменения защищённого контракта/алгоритма, зафиксировать проблему и запросить отдельное разрешение на это изменение, продолжая независимую UI-работу.

## Дизайн-философия

Создавать профессиональный enterprise-интерфейс с узнаваемой идентичностью ALROSA IT. Не копировать визуальный язык других продуктов.

Избегать generic SaaS dashboards, бессмысленных градиентов, избыточного glassmorphism, огромных скруглений, бесконечных одинаковых карточек, декоративных иконок без назначения, необоснованных анимаций и шаблонных композиций.

Предпочитать сильную типографическую иерархию, плотные читаемые таблицы, модульную сетку, сдержанную технологичную палитру, семантические статусы, контекстные действия, профессиональную визуализацию, полезные микроинтеракции. Плотность не должна ухудшать читаемость и доступность. Сохранять русскую терминологию, единицы измерения и стабильное выравнивание чисел.

Отдельно показывать «совместимо», «вероятно совместимо», «требует проверки», «несовместимо», «нет данных», только если есть основания для соответствующей оценки. Это семантика UI, не разрешение добавлять enum/пересчитывать статусы. Готовность к волне, наличие аналога, прогноз риска и подтверждённая совместимость — разные понятия. Отсутствие блокера или данных не означает успешную проверку. Цвет всегда дополнять текстом, при необходимости причиной и источником.

Главные сценарии: реестр и детали устройства; импорт и его ошибки; аппаратная и программная оценка; готовность, причины, рекомендации; сводка парка, волны, экспорт и печать; каталог, политики/NLP, ML и конфигуратор.

## Проверки будущих UI-изменений

- Зафиксировать начальный git status; не откатывать чужие изменения. Проверить diff на выход за согласованный объём.
- Сравнивать одинаковый набор данных, ОС и критерии до/после: ID, численность, статусы, волны, причины, значения, действия и экспорт должны сохраняться.
- Проверять desktop, узкие экраны, масштаб 200%, длинные значения, большую выборку, пустой парк, неизвестные данные, loading и ошибки. Таблицы могут прокручиваться внутри контейнера, действия должны оставаться доступны.
- Проверять клавиатуру, видимый фокус, подписи полей, семантику таблиц/диалогов, возврат фокуса, контраст WCAG AA и prefers-reduced-motion. Не кодировать статус только цветом.
- Использовать Playwright для визуальной проверки, если доступен рабочий runtime и браузер. Само наличие скилла не подтверждает работоспособность. При недоступности явно сообщить ограничение; не устанавливать зависимости без согласования и не выдавать статический просмотр кода за браузерный тест.
- Доступные команды frontend: `npm run build`, `npm run lint` в `frontend`; backend-тесты находятся в `backend/tests` и запускаются в подготовленном окружении. Выбирать проверки по изменениям, не запускать импорт в рабочую БД ради визуального теста без соответствующего разрешения.
